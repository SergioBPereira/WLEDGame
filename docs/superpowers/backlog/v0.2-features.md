# WLED Game — v0.2+ backlog

Features that came up during v0.1 brainstorming but were explicitly deferred. Each item should grow into its own design + plan when we pick it up.

## A. Levels and bosses (highest priority for v0.2)

Inspired by `worksasdesigned/1D-RGB-Invader`. They balanced 10 levels and 3 bosses on a 240-LED strip; their constants are in `1D_SOUND.ino` in their repo and are worth reading for tuning.

Concrete targets:

- **10 levels** with handcrafted spawn patterns (not just continuous ramps). Each level has a fixed enemy count + composition (e.g., level 3 = 12 enemies, mostly R, one G "elite").
- **3 bosses** between levels (e.g., after level 4, 7, 10):
  - *Masterblaster* — fast single enemy with high "HP" (must be hit N times of correct color, color cycles).
  - *The Tank* — slow but takes wrong-color shots without pushing it forward (immune to stuck mode).
  - *RGB Overlord* — endgame boss; spawns minions.
- **Level transition screen** — brief "Level N!" overlay on the strip + the UI, ~1.5 s pause.
- **Bonus stage** — triggers on full-clear of a level under time threshold; rapid same-color enemies, double points.
- **Endless mode** — unlocked after RGB Overlord defeated, picks up at level 11 and never stops scaling.

Architecture hook in v0.1: gameplay code reads from a `Level` interface (`spawnPattern(t, score)`, `speedFn(t, score)`, `nextEnemy()`). v0.1 ships one `EndlessLevel` instance. v0.2 adds 10 + 3 boss-level implementations behind the same interface.

## B. Kids mode tuning per level

v0.1 has a single kids-mode flag (slower, no ramp). v0.2 should have **per-level** kids-mode tuning so beginner players can still feel level progression without difficulty cliffs. Probably a `kidsTuning` field on each `Level`.

## C. Settings page

In-browser admin page (separate route, e.g., `/admin`) for live tuning of:
- Difficulty constants
- Color brightness / palette tweaks
- Per-WLED `fireZoneLeds` override
- Per-WLED default level / kids-mode
- Score table reset

Saves to `/var/lib/wledgame/settings.json`. Hot-reloaded by the service on save.

## D. High-score persistence

Per-WLED top-10 scores. Persisted at `/var/lib/wledgame/highscores.json`. Shown on the start screen and during the game-over screen. Optional player name input on a new high score.

## E. Sound

Audio cues on the *browser* (not the WLED). Short WebAudio synth blips for shoot / hit / miss / stuck / level-up / game-over. Mute toggle. Reason for browser-side: the WLED has no speaker; the controller phone is right next to the player.

## F. Auth / multi-room

Right now the service is unauthenticated and assumes one game room. If we ever serve multiple physical rooms from one CT:
- Per-room state (one game per WLED).
- Optional pin/password on each room.
- Player nicknames in the WS protocol.

## G. Custom enemy patterns / level editor

JSON-defined level files in a `levels/` directory. A simple browser-based editor that lets you place enemies on a virtual timeline and preview the result on the actual strip.

## H. Spectator mode

Read-only WS connection that receives state broadcasts but cannot send `shoot`/`start`. Useful for streaming the game to a TV display.

## I. Telemetry / observability

- `/metrics` endpoint in Prometheus format (game count, average score, WLED probe failures, UDP send errors, fps).
- Structured JSON logs as an alternative to the human-readable single-line format.

## J. UDP send batching / optimization

If we hit packet-loss issues at high frame rates on long strips, investigate:
- WLED's `WARLS` protocol (only sends changed pixels) — much smaller per-frame for sparse scenes like ours.
- Adaptive frame-rate based on ACK latency.

## K. Mobile UI polish

- Landscape mode optimized layout (3 buttons across the bottom of a wide phone).
- Haptic intensity setting (some Androids are too vibrate-happy).
- Larger hit-targets / accessibility mode.

## M. White ("W") multi-color enemy

A new enemy class that requires hits from **all three colors** to defeat. Tightly coupled with stuck-at-front mode.

### Mechanic

Each W enemy carries a **remaining-color set** (subset of `{R, G, B}`), starting full = `{R, G, B}` (renders as white).

On collision with an incoming shot of color `C`:

- **If `C` is in the set:** remove `C` from the set. Shot consumed. The enemy's render color updates to the sum of the remaining mask. When the set becomes empty, the enemy is defeated; score awarded.
- **If `C` is NOT in the set** (color was already cleared):
  - In **consumed mode**: shot disappears, enemy unchanged.
  - In **stuck-at-front mode**: existing rule applies — the shot becomes a new head attached to the fire-facing side of the (now mixed) cluster. The W enemy retains its current color set; the stuck shot is a separate single-color head that the player must clear normally before reaching the W enemy again.

### Display color (set → render)

| Remaining set | Render color | Mnemonic |
|---|---|---|
| `{R, G, B}` | white | full |
| `{G, B}` | cyan | "G+B" |
| `{R, B}` | magenta | "R+B" |
| `{R, G}` | yellow | "R+G" |
| `{R}` | red | last one |
| `{G}` | green | last one |
| `{B}` | blue | last one |
| `{}` | (defeated) | removed |

### Worked example (stuck mode)

`FFFF---W---B`, set = `{R,G,B}`, render white.

- Shoot R → set becomes `{G,B}`, W renders cyan: `FFFF---c---B`.
- Shoot R again (R no longer in set) → R sticks in front of cyan W: `FFFF--Rc---B` (cluster `Rc`, head R, cyan W trailing).
- Shoot R (matches head R) → R dissolves: `FFFF---c---B`. Player must now hit cyan W with G or B.
- Shoot B → set becomes `{G}`, W renders green: `FFFF---g---B`.
- Shoot G → set empty → W defeated, score +1 (or +3 — see scoring decision below).

### Open questions for v0.2 design

- Scoring for W enemies: `+1` total (treat as one entity), `+3` (one per color cleared), or `+1 per clear + bonus on full defeat`?
- Spawn rate: what fraction of enemies are W? (Suggest start ~5% at score 0, ramping to ~15%.)
- Does kids mode include W enemies, or skip them?
- v0.1 → v0.2 data model: enemy `color: 'R'|'G'|'B'` becomes `colorMask: number` (R=1, G=2, B=4). Note in v0.1 design — keep enemy color access narrow so this refactor is mechanical.

## N. Tunnel zones (occlusion regions)

Per-fixture configurable regions of the strip that render as a fixed low-brightness color and **occlude** any entity passing through them. Adds a "blind spot" mechanic — the player must time shots to coincide with enemy emergence at the far edge of the tunnel.

### Config

Per-WLED in `wleds.json`:

```json
{
  "wleds": [
    {
      "host": "10.0.0.11",
      "tunnels": [
        { "startLed": 20, "endLed": 30, "color": "#553311", "brightness": 0.10 },
        { "startLed": 75, "endLed": 95, "color": "#222244", "brightness": 0.15 }
      ]
    }
  ]
}
```

### Mechanics

- **Render:** tunnel LEDs always show their fixed color × brightness. Entities whose render LEDs fall inside any tunnel range are **not drawn** — but they still exist, still move, and still collide.
- **Shots:** travel through tunnels invisibly. Collision math doesn't change.
- **Lead-enemy emphasis** (§5.8 of v0.1) is suppressed while the lead is inside a tunnel — no flicker through the wall.
- **Game over** still triggers when a cluster's leading edge crosses the fire boundary, regardless of whether it was visible just before. (This makes long tunnels right before the fire zone genuinely tense.)
- **Locked at round start** — tunnel config can't change mid-round.

### Open questions

- Is occlusion strict (entities in a tunnel are 100% invisible) or partial (40% transparency, can be glimpsed)? Strict is simpler and tenser.
- Should tunnels override background rendering (yes, by definition) and fire zone rendering (no — refuse to overlap; if `endLed > ledCount - fireZoneLeds`, log a config error and clamp).
- Per-tunnel SFX cues for entry/exit (browser-side audio)?
- Visual cue at the tunnel mouths when an enemy is *about* to emerge (e.g., faint pulse)? Adds skill ceiling while keeping the blindness honest.

### v0.1 → v0.2 implications

v0.1 should keep rendering modular enough that "skip drawing entities at LEDs in set X" is a single masking step at the end of the entity layer. No data-model changes required.

## L. Multi-strip levels

If a level can use multiple WLEDs simultaneously (e.g., one fixture is the "main world", another is a "background ambience"), treat the WLED list as a *team* rather than a single pick.

## O. On-demand reprobe of offline WLEDs

v0.1 only probes WLEDs once at server startup. If the network or the WLED is briefly unreachable at boot, the WLED stays marked `online: false` until the service is restarted — even after it comes back. This is the failure mode that motivated the feature.

### Behavior

When a client hits the server (HTTP `/`, HTTP `/api/wleds`, or WS connect / `hello`), if **any** WLED is currently `online: false`, kick off a reprobe of just the offline ones. Non-blocking — don't delay the response.

- **Debounce**: at most one reprobe per ~10 s, regardless of how many requests arrive. A reload storm must not hammer the WLEDs with `/json/info`.
- **Single-flight**: if a reprobe is already in flight, subsequent triggers join it instead of starting a second one.
- **On change, broadcast**: when a previously-offline WLED comes back, broadcast a fresh `hello` to all connected WS clients so the UI updates without a page reload.
- **Online WLEDs are not touched** — this is reprobe-of-offline, not reprobe-of-all. (`probeAll` still exists for startup.)

### Open questions

- Should we also run a periodic background reprobe (e.g., every 60 s) independent of client traffic, so a passive observer doesn't have to refresh? Probably yes, but only after the on-demand path is in.
- Surface `lastError` in `/api/wleds` for debugging, or keep it server-side only?
